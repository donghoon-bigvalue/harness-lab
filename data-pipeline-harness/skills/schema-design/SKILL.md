# Schema Design — 데이터 모델·스키마 설계

파이프라인의 **계약**을 만든다. 목표는 테이블 나열이 아니라, ETL·검증·모니터링이 참조할 **E번호·필드 ID로 색인된 엔티티/필드 카탈로그**를 만드는 것이다. 이 색인이 팀 전체의 정렬 축이다.

## 설계 절차

### 1. 타겟 사용처에서 역산한다
원천 구조를 그대로 복제하지 않는다. 데이터가 **어떻게 쓰일지**가 모델을 정한다:
- 분석/리포팅 → 스타 스키마(팩트+디멘전), 역정규화 허용
- 운영/트랜잭션(OLTP) → 정규화, 무결성 우선
- ML 피처 → 넓은 피처 테이블, 시점 정합성(point-in-time)
- 조회 패턴(어떤 필터·조인·집계가 잦은가)이 파티셔닝·인덱스를 정한다

### 2. 그레인을 못 박는다
각 엔티티에서 **"1행이 무엇을 의미하는가"**를 한 문장으로 확정한다. 이것이 없으면 집계·조인이 전부 어긋난다.
- "주문 팩트"인가 "주문 품목 팩트"인가 — 그레인이 다르면 매출 합계가 달라진다
- 한 엔티티에 서로 다른 그레인이 섞이면 엔티티를 분리한다

### 3. 필드·타입·제약을 정의한다
필드마다 다음을 모두 명시한다. 비워두면 하류가 계약을 해석 못 한다:
- **타입**: 도메인에 맞춰 정한다(원천이 아니라). 금액은 `DECIMAL`, 식별자는 정수/UUID, 시각은 타임존 포함. 정확도가 중요한 값에 `FLOAT` 금지
- **널 허용**: NOT NULL인지 명시. NOT NULL은 ETL이 보장하거나 기본값이 있어야 하는 계약
- **키**: PK(그레인과 일치), FK(참조 무결성)
- **제약**: UNIQUE, CHECK(범위·열거), 기본값

### 4. 물리 설계는 규모에서 나온다
데이터 규모·조회 패턴을 근거로 결정한다. 소규모면 과설계를 피한다:
- **파티셔닝**: 대용량 팩트는 날짜/키로 파티션(스캔·수명주기 관리)
- **클러스터링/인덱스**: 잦은 필터·조인 키
- **적재 방식 힌트**: 그레인·주기를 근거로 ETL에 전체/증분/병합 방향 제안(확정은 ETL과 협의)

### 5. 카탈로그를 색인한다
위 전부를 E번호·필드 ID로 색인해 발행한다. 이 색인이 없으면 통합 리뷰가 대조할 축이 없다.

- 정규화/역정규화 결정과 이유

## 핵심 원칙

- **그레인 먼저, 필드는 그다음.** 그레인이 모호하면 어떤 필드도 신뢰할 수 없다.
- **모든 제약을 명시한다.** NOT NULL·CHECK·UNIQUE·FK는 검증·ETL이 지켜야 할 계약이다. 비워두면 하류가 무엇을 지킬지 모른다.
- **타입은 도메인에서, 물리는 규모에서.** 원천 타입을 복제하지 않고, 규모 없는 과설계도 하지 않는다.
- **E번호·필드 ID 색인은 필수다.** 색인이 없으면 ETL·검증·모니터링이 대상을 지목할 수 없고 정합성 검증이 불가능하다.
- **원천 미확인은 표기한다.** 가정한 타입·제약에 "원천 미확인"을 달아 검증·ETL이 위험을 알게 한다. 지어내지 않는다.
