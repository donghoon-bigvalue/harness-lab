# Description Writing — API 설명 작성

추출된 엔드포인트 레코드를 사람이 읽고 쓸 수 있는 설명으로 옮기고, 최종 레퍼런스 문서의 뼈대를 세운다. 코드가 "무엇인지"를 말했다면, 이 단계는 "무엇을 위한 것이고 어떻게 쓰는지"를 말한다.

## 작성 절차

### 1. 레코드를 사실 근거로 삼는다
`01_endpoints.md`의 각 `E번호` 레코드(`파일:라인` 근거)가 당신의 사실 원천이다. 레코드에 없는 파라미터·응답을 설명에 추가하지 않는다. 의미가 모호하면 endpoint-analyzer에게 질의한다 — 추측으로 메우지 않는다. 당신이 채우는 것은 타입 뒤의 **의미·용례·계약**이다.

### 2. 엔드포인트별 개요를 쓴다
"무엇을 반환한다"에서 멈추지 않는다. 무엇을 위한 동작인지, 어떤 상황에서 호출하는지, 인접 엔드포인트(같은 리소스의 목록/상세/생성)와 어떻게 다른지를 적는다. 소비자가 "이 엔드포인트를 언제 쓰는가"에 답할 수 있어야 한다.

### 3. 파라미터를 계약으로 서술한다
타입만 나열하지 않는다. 각 파라미터에 대해:
- **필수/선택**과 **기본값**
- **허용 범위·형식**(날짜 형식, enum 값, 최대 길이, 페이지네이션 한계)
- **필드 간 제약**(예: `start`는 `end` 이전, `cursor`와 `page`는 상호 배타)
목적은 소비자가 400을 맞지 않게 하는 것이다.

### 4. 응답과 동작을 설명한다
- 성공 응답의 **주요 필드 의미**(레코드의 응답 형태 기반)
- **부수효과와 멱등성**: POST 중복 호출 시 동작, DELETE의 이미-삭제 자원 반응, 비동기 처리 여부
- **주요 에러 조건**: 어떤 입력이 어떤 상태코드를 부르는지 (상세 재현은 예제 단계지만, 조건은 여기서 설명)

### 5. 레퍼런스 문서 뼈대를 조립한다
엔드포인트별 표준 섹션으로 최종 문서(`api-reference.md`)를 세운다. 각 엔드포인트 아래 `### 예제` 자리 표시를 남겨 example-generator가 채우게 한다. 섹션 제목에 원본 `E번호`를 병기해 하류 태깅과 리뷰 대조를 유지한다.

### 6. 대상 독자에 맞춘다
`00_scope.md`가 지정한 독자에 따라 조절한다:
- **외부 소비자**: 내부 구현 용어를 피하고, 전제 지식을 줄이고, 계약(입력·출력·에러)을 명확히
- **내부 개발자**: 관련 모듈·부수효과·성능 특성 등 구현 맥락을 더 담아도 됨

## 출력 형식

`api-docs/outputs/{YYYYMMDD}-{slug}/api-reference.md` (감독자가 전달한 정확한 경로 사용). 문서 상단에 개요·인증·공통 규약을, 이어서 엔드포인트별 섹션:

```markdown
# {API 이름} 레퍼런스
> 생성: {YYYY-MM-DD} | 대상: {프레임워크/버전} | 기준 커밋/범위: {범위}

## 개요
{API가 무엇을 제공하는지, 베이스 URL, 버전}

## 인증
{공통 인증 방식 — 레코드 기반. 엔드포인트별 예외는 각 섹션에}

## 공통 규약
{페이지네이션·에러 응답 공통 형태·날짜 형식 등 반복 규약}
```

## 핵심 원칙

- **레코드를 넘어서되 배반하지 않는다.** 없는 스펙을 지어내지 않고, 모호하면 analyzer에 질의한다. 채우는 것은 의미·용례.
- **"왜/언제"를 설명한다.** 타입 재진술은 무가치하다. 사용 맥락과 인접 엔드포인트와의 차이를 적는다.
- **파라미터는 계약으로 쓴다.** 필수·기본값·범위·필드 간 제약. 소비자의 400을 예방한다.
- **부수효과·멱등성을 명시한다.** 중복 호출·재시도 안전성은 소비자에게 치명적이다.
- **확인 불가는 그대로 표기한다.** 레코드가 "확인 불가"인 부분은 "코드에서 확인되지 않음 — 런타임 검증 필요"로 남기고 상상으로 채우지 않는다.
- **뼈대를 온전히 세운다.** E번호 전량이 섹션으로 존재하고 예제 자리 표시가 있어야 example-generator가 이어받고 리뷰어가 커버리지를 대조할 수 있다.
