# Endpoint Analysis — API 표면 정적 추출

코드가 실제로 노출하는 API를 소스에서 추출한다. 목표는 라우트 나열이 아니라, **하류 팀원과 리뷰어가 정렬·대조할 수 있는, `파일:라인` 근거가 붙은 엔드포인트 레코드**를 만드는 것이다. 이 산출물이 파이프라인 전체의 진실 원천이다.

## 분석 절차

### 1. 라우트 등록 지점 탐색
프레임워크마다 엔드포인트를 등록하는 방식이 다르다. 등록 지점을 찾으면 열거가 완결된다. **프레임워크별 탐색 전략은 `${CLAUDE_PLUGIN_ROOT}/skills/endpoint-analysis/references/frameworks.md`를 읽어라**(플러그인 설치 경로로 치환된 절대 경로를 Read 툴에 넘긴다) — 감지된 스택에 해당하는 섹션만 로드하면 된다.

공통 진입 전략:
- **설정/부트스트랩 파일**: 앱 초기화 지점(`app.js`, `main.py`, `urls.py`, `routes.rb`, `*Application.java`)에서 라우터 마운트를 찾는다
- **데코레이터/애노테이션 grep**: `@app.route`, `@Get`, `@RequestMapping`, `@RestController`, `router.get(` 등 라우트 표식을 전역 검색한다
- **규약 디렉토리**: 파일 기반 라우팅(Next.js `app/`·`pages/api/`, Nuxt `server/api/`)은 디렉토리 구조 자체가 라우트다

세 전략 중 하나로 등록부를 확정한다. 마운트 접두사(`app.use('/api/v1', router)`)를 놓치면 전 경로가 틀리므로, 중첩 라우터의 접두사를 끝까지 이어 붙인다.

### 2. 엔드포인트별 계약 추출
각 엔드포인트에서 다음을 핸들러·미들웨어를 따라 읽어 추출한다. **모든 항목에 `파일:라인` 근거를 붙인다:**
- **경로/쿼리/헤더 파라미터**: 핸들러가 실제 읽는 것(`req.params`, `req.query`, `@PathVariable`, `request.args`, 함수 시그니처의 타입 힌트)
- **요청 본문**: 검증 스키마·DTO·직렬화 클래스에서 필드와 필수 여부를 읽는다 (Pydantic 모델, zod 스키마, Java DTO, `strong_params`)
- **응답 형태**: 핸들러가 무엇을 반환/직렬화하는지 추적한다 — 리턴 객체, serializer, `res.json(...)`, 스키마. 라우트 시그니처만 보고 지어내지 않는다
- **상태코드**: 성공(200/201/204)과 명시적 에러(`throw`, `res.status(4xx)`, 예외 핸들러)
- **인증**: 미들웨어·가드·데코레이터(`@auth`, `requireAuth`, `Depends(get_current_user)`, `before_action`)에서 요구 여부와 스킴
- **부수효과**: DB 쓰기, 외부 API 호출, 이벤트/큐 발행

### 3. 중간 계층 확인
인증·검증·페이지네이션·공통 헤더는 흔히 미들웨어·데코레이터·가드에 있다. 라우터에 걸린 전역/그룹 미들웨어를 확인해, 핸들러 본문에 없는 공통 파라미터·인증 요구를 놓치지 않는다.

### 4. 엔드포인트 레코드 작성
E번호를 전역 연속으로 부여한다. 이 번호가 팀 전체의 색인이다.

### 5. 커버리지 정직성
확실히 추출한 것과 코드만으로 불명확한 것을 구분한다. 동적 조립·환경 분기·외부 프록시는 "확인 불가"로 남긴다. 이것이 다음 단계의 신뢰 근거이자 리뷰어의 점검 지점이 된다.

## 출력 형식

`api-docs/_workspace/01_endpoints.md` (감독자가 전달한 정확한 경로 사용):

```markdown
# 엔드포인트 인벤토리
> 추출시점: {YYYY-MM-DD} | 프레임워크: {감지된 스택} | 추출 모드: {정상 | 제한적}

## {리소스/모듈 그룹명}

### E1. {METHOD} {전체 경로 — 마운트 접두사 포함}
- 소스: {파일:라인 — 라우트 등록 지점}
- 핸들러: {파일:라인 — 처리 함수}
- 인증: {불필요 | 필요(스킴/스코프) — 파일:라인}
- 경로 파라미터: {name: 타입 — 제약 | 없음}
- 쿼리 파라미터: {name: 타입 — 필수·기본값 | 없음}
- 요청 본문: {필드(필수표시)·타입 | 없음 — 파일:라인}
- 성공 응답: {상태코드: 형태(필드/타입) — 파일:라인}
- 에러 응답: {상태코드: 조건 — 코드에서 확인된 것만}
- 부수효과: {DB·외부호출·이벤트 | 없음}
- 확인 불가: {코드만으로 결정 못 한 항목 | 없음}

### E2. ...

## 추출 커버리지
- 추출된 엔드포인트: {총 개수, E번호 범위}
- 확인 불가/부분 추출: {E번호 + 무엇이 왜 불명확한지}
- 재추출/검증 요청 지점: {어떤 엔드포인트를 어느 팀원에 넘겼는지}
```

## 핵심 원칙

- **코드가 말한 것만 적는다.** 관례상 있을 법한 파라미터를 추측으로 넣지 않는다. 근거는 항상 `파일:라인`.
- **마운트 접두사를 끝까지 이어 붙인다.** 경로 하나가 틀리면 그 엔드포인트의 모든 예제가 401/404를 부른다.
- **응답은 직렬화 지점에서 읽는다.** 리턴 객체·serializer를 추적하고, 못 하면 "확인 불가"로 남긴다.
- **추출 실패 시 폴백을 선언한다.** 3개 전략이 다 실패하면 상단에 "추출 모드: 제한적"을 명시하고 확인된 것만 남긴다. 없는 엔드포인트를 지어내는 것이 가장 큰 실패다.
- **못 찾은 것을 기록하는 것도 결과다.** 커버리지 섹션의 "확인 불가"는 하류가 신뢰도를 낮추고 리뷰어가 소스를 재대조하는 근거가 된다.
