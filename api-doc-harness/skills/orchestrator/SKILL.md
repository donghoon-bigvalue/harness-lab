# API Documentation Orchestrator

문서 팀을 조율하여 **범위 설정 → 엔드포인트 분석 → 설명 작성 → 예제 생성 → 완성도 리뷰**까지 파이프라인으로 수행하고, 코드 근거가 붙은 API 레퍼런스 문서를 산출한다.

## 실행 모드: 에이전트 팀 (파이프라인 + 생성-검증 루프)

작업은 순차 파이프라인(분석 → 설명 → 예제 → 리뷰)이지만 실행은 에이전트 팀 모드다. 단계 간 직접 통신이 품질의 핵심 동력이기 때문이다 — 설명·예제 작성 중 스펙이 모호하면 즉시 analyzer에게 되묻고, 리뷰어가 찾은 불일치는 리드를 일일이 경유하지 않고 담당 팀원에게 직접 반송되어 고쳐진다. 이 교환을 리드가 전부 중계하면 병목이 되고 신호가 손실된다. 파이프라인의 순서는 작업 의존성이지 통신 제약이 아니다.

## 경로 규약

이 하네스는 플러그인으로 배포된다. **모든 산출물 경로는 하네스를 실행 중인 프로젝트의 루트 기준 상대 경로**이며, 플러그인이 어디에 설치되었는지와 무관하다. 작업 루트는 `api-docs/`다.

| 용도 | 경로 |
|------|------|
| 중간 산출물 | `api-docs/_workspace/` |
| 최종 산출물 | `api-docs/outputs/{YYYYMMDD}-{slug}/api-reference.md` |

에이전트 정의와 스킬은 플러그인이 제공하므로 **경로로 참조하지 않는다.** 에이전트는 `subagent_type`으로, 스킬은 Skill 툴의 스킬명으로 호출한다.

## 팀 구성

리더는 이 스킬을 실행하는 메인 세션이며, 문서 리드 역할을 수행한다. 시작 시 `api-doc-harness:doc-lead` 정의를 리드 원칙으로 적용한다 — 메인 세션이 리더이므로 이 에이전트를 별도로 띄우지 않는다.

| 팀원 (`subagent_type`) | 사용 스킬 | 출력 |
|------|----------|------|
| `api-doc-harness:endpoint-analyzer` | `api-doc-harness:endpoint-analysis` | `01_endpoints.md` |
| `api-doc-harness:description-writer` | `api-doc-harness:description-writing` | `outputs/.../api-reference.md` (뼈대 + 설명) |
| `api-doc-harness:example-generator` | `api-doc-harness:example-generation` | 같은 `api-reference.md` (예제 채움) |
| `api-doc-harness:completeness-reviewer` | `api-doc-harness:completeness-review` | `04_review.md` |

**팀원 생성 방식:** 위 표의 `subagent_type`을 그대로 사용한다. 플러그인이 배포한 에이전트 정의가 자동 등록되므로 정의 파일을 Read시키는 우회는 필요 없다 — 역할·원칙·통신 프로토콜이 시스템 프롬프트로 이미 주입된 상태로 기동한다. `model`은 전원 `opus`.

**프롬프트 필수 요소 (전 팀원 공통):** 에이전트 정의에는 역할만 있고 이번 실행의 경로·대상은 없다. 팀원은 프로젝트 루트에서 실행되므로 다음이 빠지면 파일을 엉뚱한 위치에 쓰거나 엉뚱한 것을 문서화한다.
1. **문서화 대상 범위**(대상 경로·모듈·프레임워크·엔드포인트 ID 집합)
2. **입력 파일의 `api-docs/_workspace/...` 또는 `outputs/...` 전체 경로**
3. **출력 파일의 전체 경로** (`{YYYYMMDD}-{slug}` 실제값 치환)

## 워크플로우

### Phase 0: 컨텍스트 확인

`api-docs/_workspace/` 존재 여부로 실행 모드를 정한다.

| 상태 | 모드 | 행동 |
|------|------|------|
| 미존재 | **초기 실행** | Phase 1로 진행 |
| 존재 + 사용자가 부분 수정 요청 | **부분 재실행** | Phase 1 건너뛰고 아래 "부분 재실행" 절차 |
| 존재 + 새 대상/새 코드베이스 | **새 실행** | `api-docs/_workspace/`를 `api-docs/_workspace_{YYYYMMDD_HHMMSS}/`로 이동 후 Phase 1 |

애매하면 사용자에게 묻는다. 기존 문서를 덮어쓰는 것은 되돌리기 어렵기 때문이다.

**부분 재실행 절차:**
1. 어떤 산출물이 대상인지 특정한다 (예: "E5 응답이 틀림" → endpoint-analyzer 재추출 + 하류 갱신 / "예제에 파이썬 추가" → example-generator / "인증 엔드포인트 설명이 얕다" → description-writer)
2. 해당 팀원만 포함해 팀을 구성한다. 추출·설명·예제가 바뀌면 completeness-reviewer를 함께 소집해 영향받는 `E번호`만 재검수한다
3. 팀원 프롬프트에 **이전 산출물 경로 + 사용자 피드백 원문**을 그대로 포함한다. 요약하지 않는다 — 요약 과정에서 사용자가 지적한 뉘앙스가 사라진다
4. 수정이 문서 본문에 반영됐는지 확인하고 Phase 5로 진행한다

### Phase 1: 범위 설정 (리드 단독 + 사용자 확인)

**실행 방식:** 문서 리드(메인 세션) 단독. 팀원을 아직 띄우지 않는다.

1. 사용자 입력에서 다음을 파악한다. 없으면 코드베이스를 살펴 감지하고 제안한다:
   - **대상 코드베이스/모듈** (필수) — 어느 디렉토리·서비스의 API인가
   - **API 종류·프레임워크** — REST/GraphQL/RPC, Express/FastAPI/Spring/Rails/Gin 등 (코드에서 감지)
   - **범위** — 전 엔드포인트인지 특정 모듈·태그·버전인지 (엔드포인트가 많으면 우선순위)
   - **출력 형식·독자** — 사람이 읽는 레퍼런스(기본) / OpenAPI 명세 병행 / 대상이 내부 개발자인지 외부 소비자인지, 예제 언어
2. 코드베이스를 가볍게 탐색해 **라우트 등록 방식과 대략의 엔드포인트 규모**를 파악한다 (전수 추출은 Phase 2에서). API가 감지되지 않으면 사용자에게 대상 경로를 확인한다.
3. `api-docs/_workspace/` 생성
4. 파악한 대상·프레임워크·범위·형식·독자를 `api-docs/_workspace/00_scope.md`에 기록 (사용자 요청 원문 포함).
5. **사용자에게 범위와 대략의 엔드포인트 규모를 제시하고 승인받는다.** 대형 코드베이스에서 범위가 흐릿하면 파이프라인 전체가 얕아지거나 엉뚱한 API를 문서화한다. 사용자가 범위를 좁히거나 넓히면 반영한다.

### Phase 2: 엔드포인트 분석 (파이프라인 1단계)

**실행 방식:** 에이전트 팀 (endpoint-analyzer 단독 기동, 이후 팀 유지)

1. 팀 생성 (analyzer 먼저):
   ```
   TeamCreate(
     team_name: "api-doc-team",
     members: [
       { name: "endpoint-analyzer",
         agent_type: "api-doc-harness:endpoint-analyzer", model: "opus",
         prompt: "대상 범위: {00_scope.md의 대상 경로·프레임워크·모듈}.
                  전 엔드포인트를 E번호로 추출.
                  입력: api-docs/_workspace/00_scope.md
                  출력: api-docs/_workspace/01_endpoints.md" }
     ]
   )
   ```
2. TaskCreate: "대상 범위의 전 엔드포인트를 레코드 형식으로 추출 → `01_endpoints.md`"
3. analyzer가 라우트 등록 지점을 찾아 엔드포인트를 열거하고, 각 엔드포인트의 계약(파라미터·응답·인증·부수효과)을 `파일:라인` 근거와 함께 추출한다
4. 완료 → 리드가 `01_endpoints.md`의 **커버리지 요약**을 확인한다. "확인 불가" 항목과 폴백 모드 여부를 점검한다
5. analyzer가 "범위를 뒤집는 발견"(동적 라우팅으로 정적 추출 불가, 대상이 실제로는 GraphQL 등)을 보고하면 Phase 1로 돌아가 범위·전략을 재설계한다

### Phase 3: 설명 작성 (파이프라인 2단계)

**실행 방식:** 에이전트 팀 (description-writer 합류, analyzer 대기)

1. description-writer 소집, 입력으로 `00_scope.md` + `01_endpoints.md`, 출력은 최종 경로 지정
2. TaskCreate: "엔드포인트별 설명 작성 + 레퍼런스 문서 뼈대 조립 → `outputs/{date}-{slug}/api-reference.md`. 각 엔드포인트에 `### 예제` 자리 표시 남길 것"
3. **통신 규칙 (리드를 경유하지 않는다):** description-writer가 레코드만으로 파라미터·응답 의미가 모호하면 endpoint-analyzer에게 직접 질의한다. 스펙을 추측으로 메우지 않기 위함이다. analyzer는 대기 상태로 질의에 답한다
4. 완료 → 리드가 뼈대 구조(엔드포인트 누락 없이 E번호 전량 반영됐는지, 예제 자리 표시가 있는지) 확인

### Phase 4: 예제 생성 (파이프라인 3단계)

**실행 방식:** 에이전트 팀 (example-generator 합류)

1. example-generator 소집, 입력으로 `01_endpoints.md`(정합 기준) + `api-reference.md`(뼈대) + `00_scope.md`(예제 언어)
2. TaskCreate: "각 엔드포인트 `### 예제` 자리를 curl·언어 스니펫·요청/응답·에러 케이스로 채움. 뼈대·설명은 건드리지 말 것"
3. **통신 규칙:** example-generator가 예제를 만드는데 레코드의 응답 형태·인증이 불충분하면 endpoint-analyzer에게 질의한다. 설명과 스펙이 어긋나 보이면(설명은 선택인데 코드상 필수) description-writer에게 공유한다
4. 완료 → 리드가 예제가 전 엔드포인트에 채워졌는지, 인증 필요 엔드포인트에 인증 헤더가 있는지 훑는다

### Phase 5: 완성도 리뷰 및 보강 루프 (파이프라인 4단계)

**실행 방식:** 에이전트 팀 (completeness-reviewer 합류, 담당 팀원 대기)

1. completeness-reviewer 소집, 입력으로 `01_endpoints.md` + `api-reference.md` + **실제 소스 코드**(직접 읽음) 지정
2. TaskCreate: "커버리지·정확성·예제 정합성 교차 대조 → 심각도별 발견 목록 → `04_review.md`"
3. 리뷰어는 **문서만 보는 게 아니라 소스를 직접 열어** 레코드·문서와 3자 대조한다 (누락·유령·응답 형태 불일치·인증 누락 탐지)
4. 검수 완료 → `04_review.md`의 **심각도별 발견**과 커버리지(코드 N개 중 문서 M개) 확인
5. **치명/중대 발견 없음** → Phase 6
6. **치명/중대 발견 있음** → 보강 루프:
   - 리뷰어가 발견을 담당별로 반송한다 — 설명 문제는 description-writer, 예제 문제는 example-generator, 추출 오류는 endpoint-analyzer에게 `E번호` + 근거 `파일:라인`과 함께 SendMessage
   - 담당 팀원이 해당 `E번호` 섹션만 갱신한다 (전면 재작업 아님)
   - 추출이 바뀌면 하류(설명·예제)도 영향받는 E번호만 갱신한다
   - completeness-reviewer가 **반송했던 항목만** 재검수 (해소 여부 + 수정이 새로 유발한 불일치)
   - **최대 2회.** 3회차 진입 시 남은 치명/중대 항목을 `04_review.md`에 "미해소"로 확정하고, 문서에 "미검증/불완전" 배지를 달아 Phase 6으로 넘어간다. 완벽을 무한히 좇는 비용이 한계효용보다 크기 때문이다

### Phase 6: 통합 및 정리

1. 리드가 최종 문서를 직접 확인한다:
   - 코드의 전 엔드포인트가 문서에 있는가 (리뷰 커버리지 수치 대조)
   - 근거 없이 단정한 스펙이 없는가 (모든 응답/파라미터에 코드 근거)
   - "확인 불가"·"미검증" 항목이 숨겨지지 않고 배지로 살아 있는가
   - 인증 필요 엔드포인트의 예제에 인증이 있는가
2. (선택) 사용자가 OpenAPI 병행을 요청했으면, 레코드·문서를 근거로 `openapi.yaml`을 함께 산출한다
3. 팀원에게 종료 알림 → `TeamDelete`
4. `api-docs/_workspace/`는 **삭제하지 않는다** (사후 검증·부분 재실행의 입력)
5. 사용자에게 요약 보고: 문서화한 엔드포인트 수, 커버리지, 남은 미검증/확인 불가 항목, 문서 경로
6. 피드백 요청: "결과에서 개선할 부분이나 팀 구성·예제 언어에서 바꾸고 싶은 점이 있나요?"

## 데이터 흐름

```
사용자 입력
    ↓
[리드] 대상·프레임워크·범위 파악 → 00_scope.md → 사용자 승인
    ↓
endpoint-analyzer → 01_endpoints.md (E번호 + 파일:라인 근거 = 진실 원천)
    ↓ (스펙 모호 시 ←질의)
description-writer → api-reference.md (뼈대 + 설명, 예제 자리 표시)
    ↓ (스펙/설명 확인 시 ←질의)
example-generator → api-reference.md (예제 채움: curl·스니펫·요청/응답·에러)
    ↓
completeness-reviewer ── 소스 코드 직접 대조 ──→ 04_review.md (심각도별 발견)
    ↓ 치명/중대 발견 → 담당 팀원에 반송(최대 2회) ↺
    ↓ (설명→writer, 예제→generator, 추출오류→analyzer)
[리드] 커버리지·정확성 최종 확인 → (선택) openapi.yaml
    ↓
outputs/{date}-{slug}/api-reference.md
    ↓
[리드: 최종 확인 + 사용자 보고]
```

|------|------|
| 라우트 등록 지점 못 찾음 | analyzer가 3개 전략(설정·데코레이터·규약 디렉토리) 실패 시 폴백 선언 → `01_endpoints.md` 상단 "추출 모드: 제한적" → 확인된 엔드포인트만. 없는 엔드포인트를 지어내지 않는다 |
| 동적 라우팅으로 정적 추출 불가 | 추출 가능 부분과 불가 부분 분리, 불가 부분은 문서에 "코드에서 확인 불가 — 런타임 검증 필요" |
| 응답 형태 코드에서 불명확 | "확인 불가"로 표기, 예제 응답을 지어내지 않음. 리뷰어가 "런타임 검증 필요"로 통과 |
| 설명·예제가 스펙과 상충 | endpoint-analyzer의 레코드(코드 근거)를 기준으로 삼고, 상충을 리뷰어가 불일치로 반송 |
| 리뷰어가 코드가 옳고 문서가 틀렸다고 판정 | 코드 기준으로 담당 팀원에 반송. 단 코드 자체 버그 의심은 별도 표기해 사용자에 보고 |
| 팀원 1명 실패 | SendMessage로 상태 확인 → 1회 재시작 → 재실패 시 해당 단계 산출물을 "미완"으로 명시하고 진행 |
| completeness-reviewer 실패 | 리드가 `api-doc-harness:completeness-review` 스킬의 체크리스트를 직접 수행 |
| 보강 루프 3회차 | 루프 종료. 남은 치명/중대 항목을 문서 "미검증/불완전" 배지 + `04_review.md`에 기록 |
| 엔드포인트가 너무 많음(범위 초과) | 리드가 모듈·태그로 범위를 쪼개 우선순위를 사용자에 확인. 한 번에 전량을 얕게 다루지 않는다 |
| API가 감지되지 않음 | 리드가 대상 경로를 사용자에 재확인. 문서화할 API가 없으면 그 사실을 보고 |

## 테스트 시나리오

### 정상 흐름
1. 사용자: "이 Express 서버의 REST API 문서 자동으로 만들어줘"
2. Phase 1 — 리드가 `src/routes/` 감지, Express 라우터 방식 확인, 약 12개 엔드포인트 규모 파악, 독자=외부 소비자·예제 언어=curl+JS로 범위 확정, 사용자 승인
3. Phase 2 — endpoint-analyzer가 라우터 등록부에서 12개 엔드포인트를 E1~E12로 추출, 각 핸들러의 파라미터·응답·인증 미들웨어를 `파일:라인`과 함께 레코드화. `POST /orders`의 응답 형태가 동적이라 "확인 불가" 표기
4. Phase 3 — description-writer가 12개 섹션의 레퍼런스 뼈대를 세우고 설명 작성, `GET /orders` 쿼리 파라미터 의미가 모호해 analyzer에 질의 후 반영
5. Phase 4 — example-generator가 curl+JS 예제, 현실적 요청 본문, 401/400/404 에러 케이스를 채움. 인증 필요 엔드포인트 전부에 Bearer 헤더 포함
6. Phase 5 — completeness-reviewer가 소스 직접 대조: `DELETE /orders/{id}` 엔드포인트가 코드엔 있는데 문서 누락(치명) 발견 → analyzer 재추출 + writer/generator 보강 1회 → 재검수 통과
7. Phase 6 — `outputs/20260724-express-orders-api/api-reference.md` 생성, `POST /orders` 응답은 "런타임 검증 필요" 명시, 커버리지 12/12 보고
8. 예상: 전 엔드포인트가 코드 근거와 함께, 설명·예제·에러 케이스를 갖춰 문서화됨

### 에러 흐름 A — 정적 추출 제한
1. Phase 2에서 라우트가 플러그인 시스템으로 런타임 등록되어 endpoint-analyzer가 등록부를 못 찾음(3전략 실패)
2. "추출 모드: 제한적" 선언, `01_endpoints.md` 상단 명시, 정적으로 확인된 코어 엔드포인트만 레코드화
3. 리드가 Phase 1로 잠깐 복귀해 사용자에 상황 보고, 확인된 범위로 계속할지 확인
4. 문서 상단과 리뷰 커버리지에 "동적 등록 엔드포인트 미포함 — 런타임 목록 확인 필요" 명시
5. 없는 엔드포인트를 지어내지 않음

### 에러 흐름 B — 보강 루프 한도 초과
1. Phase 5 1회차: 치명 2건(E3 응답 필드 불일치, E9 인증 누락), 중대 1건(E7 에러 케이스 전무)
2. 리뷰어가 analyzer(E3 재추출)·generator(E9 인증·E7 에러)로 반송
3. 2회차: E9·E7 해소, E3는 코드가 조건별로 응답이 갈려 단일 형태로 확정 불가 → 새 상충
4. 3회차 진입 금지 → E3를 `04_review.md`에 "미해소 — 조건부 응답"으로 확정, 문서 E3 섹션에 "미검증/불완전" 배지 + 분기 조건 명시
5. Phase 6 진행, 사용자 보고 시 E3 한계 언급
