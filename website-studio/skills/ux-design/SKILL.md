# UX Design — 화면·디자인 시스템 설계

요구사항을 프론트엔드가 추측 없이 구현할 수 있는 **청사진**으로 만든다. 핵심 산출물은 `website/_workspace/00_design_spec.md`.

## 왜 이렇게 하는가

프론트가 화면을 급조하는 이유는 스펙이 "무엇을, 어떤 데이터로, 어떤 상태에서" 보여줄지 안 정해줬기 때문이다. 그래서 이 스킬은 세 가지를 강제한다: (1) 화면마다 **데이터 요구**를 명시(→ API 계약의 씨앗), (2) **디자인 토큰을 먼저** 정하고 그 위에 화면을 얹음(→ 일관성), (3) **빈/로딩/에러 상태**를 화면의 일부로 정의(→ 나중에 급조 방지).

## 절차

1. **화면 인벤토리** — 필요한 페이지/뷰를 P1, P2 … 로 나열. 각 화면: 목적, 진입 경로, 주요 액션
2. **사용자 플로우** — 핵심 시나리오를 화면 전이로 그린다 (예: `P1 랜딩 → P2 로그인 → P3 대시보드 → P4 상세`)
3. **디자인 토큰** — 화면 설계 전에 먼저 확정 (아래 표준)
4. **화면별 와이어프레임** — 구조적으로 기술 (섹션·컴포넌트 배치, 위계, 반응형 거동, 상태별 표시)
5. **컴포넌트 인벤토리** — 재사용 컴포넌트 목록 + 각 컴포넌트의 variant/상태
6. **화면별 데이터 요구** — 각 화면이 렌더하려면 어떤 필드가 필요한지. **이것이 API 계약 도출의 입력이다**

## 디자인 토큰 표준

화면마다 색을 즉흥적으로 고르면 구현이 제각각이 된다. 먼저 못박는다:

```markdown
## 디자인 토큰
- 색상: primary, secondary, background, surface, text, muted, border, success, warning, danger (각 hex + 다크모드 대응 여부)
- 타이포: 폰트 패밀리, 스케일(예: xs 12 / sm 14 / base 16 / lg 18 / xl 24 / 2xl 32), 굵기
- 간격: 스케일(예: 4 / 8 / 12 / 16 / 24 / 32 / 48)
- 모서리: radius 스케일 / 그림자: elevation 스케일
- 브레이크포인트: mobile < 640 / tablet 640~1024 / desktop > 1024
```

토큰은 프론트가 그대로 CSS 변수/Tailwind 설정/테마로 옮길 수 있게 구체적 값으로 적는다.

## 와이어프레임 표기

픽셀이 아니라 구조를 전달한다. ASCII 스케치나 계층 목록 중 명료한 쪽을 쓴다:

```markdown
### P3. 대시보드
- 진입: 로그인 성공 후 / 데이터 요구: 프로젝트 목록
- 레이아웃:
  - 상단바: 로고(좌) · 사용자 메뉴(우)
  - 본문: 프로젝트 카드 그리드 (desktop 3열 / tablet 2열 / mobile 1열)
    - 카드: 제목 · 상태 배지 · 수정일 · 클릭 시 P4 상세로 이동
  - 우하단: "새 프로젝트" FAB
- 상태:
  - 로딩: 카드 스켈레톤 6개
  - 빈 상태: "아직 프로젝트가 없어요" + 생성 CTA
  - 에러: 재시도 버튼이 있는 인라인 에러
```

## 화면별 데이터 요구 (API 계약의 입력)

각 화면 끝에 렌더에 필요한 필드를 명시한다. 백엔드는 이걸로 무슨 API를 만들지 안다:

```markdown
### P3 데이터 요구
- 프로젝트 카드 목록 — 각 항목: id, 제목, 상태(todo|doing|done), 수정일(ISO)
- 정렬: 수정일 내림차순 / 페이지네이션: MVP는 불필요
```

## 출력 형식

`website/_workspace/00_design_spec.md`:

```markdown
# 디자인 스펙 — {프로젝트명}
> 사용자 요청 원문: {...}

## 화면 인벤토리
| P번호 | 화면 | 목적 | 진입 경로 |

## 사용자 플로우
{화면 전이 다이어그램}

## 디자인 토큰
{위 표준}

## 컴포넌트 인벤토리
| 컴포넌트 | variant/상태 | 사용 화면 |

## 화면별 상세 (P1 … Pn)
{각 화면: 와이어프레임 + 상태별 + 데이터 요구}

## 접근성 노트
{대비·포커스·대체텍스트가 필요한 지점}
```

## 원칙

- **데이터 요구 없는 화면은 미완성이다.** "대시보드"만으로는 API를 못 만든다. 필드까지 내려가라.
- **상태를 빠뜨리지 마라.** 빈/로딩/에러는 화면의 일부다. 나중에 프론트가 급조하면 일관성이 깨진다.
- **오버피팅 금지.** 특정 예시 화면에만 맞는 규칙이 아니라, 도메인에 맞는 재사용 컴포넌트로 일반화하라.
- **재호출 시** `00_design_spec.md`가 있으면 지목된 화면만 갱신하고, 토큰 변경 시 영향받는 화면을 함께 알린다.
