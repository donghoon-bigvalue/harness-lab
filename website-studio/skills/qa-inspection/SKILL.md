# QA Inspection — 통합 정합성 검증

"각각은 맞는데 연결부가 어긋난" 버그를 잡는다. 웹 앱 런타임 에러의 최대 원천은 경계면 불일치다. 이 스킬은 **존재 확인이 아니라 양쪽을 동시에 열어 교차 비교**하는 절차를 제공한다.

## 왜 빌드 통과로는 부족한가

- `fetchJson<Project[]>()`는 런타임 응답이 `{ projects: [...] }`여도 컴파일을 통과한다 (제네릭의 한계)
- 캐스팅·`any`·제네릭이 끼면 `npm run build`는 성공하고 런타임에 실패한다
- "API가 있는가"와 "API 응답이 호출측 기대와 일치하는가"는 전혀 다른 검증이다

## 검증 우선순위

1. **통합 정합성** (가장 높음) — 경계면 불일치 = 런타임 크래시의 주원인
2. **기능 스펙 준수** — 계약·상태머신·데이터 모델대로 동작하는가
3. **디자인 품질** — 토큰·반응형·상태별(빈/로딩/에러) UI
4. **코드 품질** — 죽은 라우트·미사용 코드·명명 일관성

## 통합 정합성 체크리스트 (핵심)

### API ↔ 프론트엔드 연결
- [ ] 모든 API route의 응답 shape과 대응 훅의 제네릭 타입이 일치
- [ ] 래핑된 응답(`{ items: [...] }`)을 훅에서 unwrap하는지 (배열로 착각 안 하는지)
- [ ] snake_case(DB) ↔ camelCase(API) ↔ 프론트 타입 정의 필드명이 일관
- [ ] 즉시 응답(202)과 최종 결과의 shape이 프론트에서 구분되는지 (즉시 응답에서 최종 필드 접근 안 하는지)
- [ ] 모든 API 엔드포인트에 대응하는 프론트 훅이 존재하고 실제 호출됨 (1:1 매핑)
- [ ] 계약에 있는 엔드포인트가 실제 route로 존재 (누락 시 404)

### 라우팅 정합성
- [ ] 코드 내 모든 `href`/`router.push`/`redirect` 값이 실제 page 파일 경로와 매칭
- [ ] route group `(group)`이 URL에서 제거되는 것을 고려한 검증
- [ ] 동적 세그먼트 `[id]`가 올바른 파라미터로 채워짐

### 상태 머신 정합성
- [ ] 정의된 모든 상태 전이가 코드에서 실행됨 (죽은 전이 없음)
- [ ] 코드의 모든 `status` 업데이트가 전이 맵에 정의됨 (무단 전이 없음)
- [ ] 중간 상태 → 최종 상태 전환이 누락되지 않음 (프론트 영원 대기 방지)
- [ ] 프론트의 상태 분기(`if status === "X"`)의 X가 실제 도달 가능

### 데이터 흐름 정합성
- [ ] DB 컬럼명 → API 응답 필드명 매핑이 일관 (경계에서 변환됨)
- [ ] 프론트 타입 정의와 API 응답 필드명이 일치
- [ ] 옵셔널 필드의 null/undefined 처리가 양쪽에서 일관

## 검증 방법: "양쪽 동시 읽기"

한쪽만 읽으면 경계면 버그는 절대 안 잡힌다. 반드시 생산자와 소비자를 같이 연다:

| 검증 대상 | 왼쪽 (생산자) | 오른쪽 (소비자) | 추출 방법 |
|----------|-------------|---------------|----------|
| 응답 shape | `app/api/**/route.ts`의 `NextResponse.json()` | `hooks/`의 `fetchJson<T>` | grep `NextResponse.json` / grep `fetchJson<` |
| 라우팅 | `app/**/page.tsx` 경로(=URL) | `href=`, `router.push(`, `redirect(` | find page 파일 / grep 링크 |
| 상태 전이 | `STATE_TRANSITIONS` 맵 | `.update({ status` | grep 맵 / grep status 업데이트 |
| 엔드포인트 매핑 | `app/api/` route 목록 | `hooks/`의 fetch URL | find route.ts / grep fetch URL |

**절차:**
1. grep으로 양쪽 목록을 추출한다 (예: 모든 `NextResponse.json()` 인자 shape, 모든 `fetchJson<T>`의 T)
2. 각 API를 대응 훅과 **짝지어** shape을 비교 — 래핑·필드명·케이싱
3. 불일치를 파일:라인 + 무엇이 어떻게 다른지로 기록
4. 가능하면 `npm run build`·타입체크를 **실제 실행**한다 (의존성 있으면). 빌드 통과라도 위 정적 대조는 별도로 수행 — 빌드는 shape 불일치를 못 잡는다

당신은 읽기 전용이 아니다. Grep·Bash로 추출·실행하고, 명백한 경계면 수정은 직접 하거나 담당 엔지니어에게 정확한 수정을 요청한다.

## 점진 QA

전체 완성 후 1회가 아니라 **각 모듈 완성 직후** 검증한다. API 하나가 완성되면 즉시 그 API + 대응 훅의 경계면만 교차 검증. 버그 누적·전파를 막는다.

## 출력

`website/_workspace/04_qa_report.md`:

```markdown
# QA 리포트 — 통합 정합성
> 검증 방식: 정적 교차 대조 {+ npm run build 실행 여부}

## 경계면 검증 결과
| 경계면 | 생산자(파일:라인) | 소비자(파일:라인) | 판정 | 상세 |
|--------|-----------------|-----------------|------|------|
| GET /api/projects shape | route.ts:12 `{projects}` | useProjects.ts:8 `.projects` | ✅ 일치 | |
| ... | | | ❌ 불일치 | 계약은 래핑, 구현은 배열 → route.ts 래핑 추가 |

## 실패 항목 (치명도 순)
{각 실패: 파일:라인 + 불일치 + 수정 방향 + 담당(생산자/소비자)}

## 미검증 항목
{런타임 검증 못 한 부분과 이유}
```

## 원칙

- **"존재함/없음"이 아니라 "일치함/불일치(어떻게)"로 기록하라.** 존재 확인은 경계면 버그를 못 잡는다
- **경계면 이슈는 양측 모두에게 알린다.** shape 불일치는 frontend·backend 둘 다에게 파일:라인 + 수정 방향으로
- **검증 못 한 건 거짓 보고하지 않는다.** 빌드 실행 불가면 "정적 대조만"이라고 명시
- **계약이 모호해 판정 불가면** 임의로 한쪽을 정답으로 단정하지 말고 build-lead에게 계약 판정을 올린다
- **재호출 시** 전부 다시 검증하지 않고 지목된 경계면·직전 변경 모듈만 재검증
