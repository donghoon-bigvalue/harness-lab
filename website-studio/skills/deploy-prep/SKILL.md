# Deploy Prep — 배포 준비

"로컬에서 도는 앱"을 "배포 가능한 앱"으로 만든다. 환경변수·프로덕션 빌드 실패·임시 저장소·누락 의존성은 배포 순간에 터진다. 미리 잡는 게 목적.

## 왜 프로덕션 빌드를 실제로 돌리는가

개발 서버(`next dev`)가 뜬다고 배포되는 게 아니다. `next build`는 개발 중 숨어 있던 타입 에러·정적 생성 실패·환경변수 누락을 드러낸다. **빌드를 안 돌리고 "배포 준비 완료"라고 하는 것이 가장 흔한 거짓 완료다.**

## 절차

### 1. 빌드 구성 점검
- `package.json` 스크립트(`build`, `start`) 존재·정확성
- `next.config`·`tsconfig`·린트 설정이 프로덕션에 적합한지
- **타입체크/린트를 끄는 우회 설정(`ignoreBuildErrors`, `ignoreDuringBuilds`)이 있으면 플래그** — 문제를 프로덕션으로 미루는 것

### 2. 환경변수 역추적
README를 믿지 말고 코드에서 실제 필요한 변수를 grep으로 수집한다:
```
grep -rn "process.env" website/
```
- 수집한 변수를 `.env.example`에 문서화 (값 없이 키만)
- `NEXT_PUBLIC_` 접두사 여부 확인 (클라이언트 노출 변수)
- 하드코딩된 비밀·URL을 발견하면 환경변수로 빼도록 플래그

### 3. 프로덕션 빌드 실행 (핵심)
```
cd website && npm install && npm run build
```
- **통과**: 빌드 로그를 증거로 체크리스트에 기록
- **실패**: 원인을 로그에서 특정 → 담당 엔지니어에게 수정 요청. 우회 설정으로 억지 통과 금지
- 의존성 미설치 등으로 실행 불가면 "빌드 미실행 — 사유"를 명시. 통과했다고 거짓 보고하지 않는다

### 4. 배포 대상 구성
지정된 대상에 맞춘다:

| 대상 | 확인 항목 | 산출 파일 |
|------|----------|----------|
| Vercel (기본) | 서버리스 함수 제약, 빌드 명령 자동 감지 | (선택) `vercel.json` |
| Docker | 런타임·포트·멀티스테이지 빌드 | `Dockerfile`, `.dockerignore` |
| 정적 호스팅 | SSR/Route Handler 불가 — `output: export` 가능한지 | `next.config` 조정 |
| 노드 서버 | `next start` 프로세스·포트·리버스 프록시 | 실행 절차 문서 |

미지정이면 기본값(Vercel 호환 표준 Next.js)을 제안하고 "확인 필요"로 남긴다.

### 5. 배포 전 리스크 플래그
프로덕션에서 깨질 항목을 체크리스트에 승격한다:
- **임시 인메모리/파일 저장소** → 배포 시 데이터 휘발 → "배포 전 DB 교체 필요"
- **목 데이터·하드코딩 URL** → 실제 환경에서 깨짐
- **`04_qa_report.md`의 미해결 경계면 이슈** → 배포 전 확인 대상으로 인계

## 출력

`website/_workspace/05_deploy_checklist.md`:

```markdown
# 배포 체크리스트 — {프로젝트명}

## 프로덕션 빌드
- 실행: `npm run build` / 결과: ✅ 통과 | ❌ 실패({사유}) | ⚠️ 미실행({사유})
- {빌드 로그 요약 — 증거}

## 환경변수
| 변수 | 용도 | 클라이언트 노출 | 필수 |
{.env.example 대응}

## 배포 대상: {대상}
- 구성 파일: {생성한 파일}
- 배포 명령/절차: {사용자가 실행할 단계}

## 배포 전 리스크
- [ ] {임시 저장소 → 교체 필요}
- [ ] {미해결 QA 이슈}

## 앱 실행법
- 개발: `cd website && npm install && npm run dev`
- 프로덕션: `npm run build && npm start`
```

## 원칙

- **빌드 통과를 증거로 남겨라.** 실제 실행 없이 준비 완료라고 하지 않는다
- **우회로 통과시키지 마라.** 타입체크·린트를 끄는 건 문제를 배포로 미루는 것 — 담당 엔지니어 수정이 정답
- **실제 배포는 사용자 권한.** 자격증명이 필요하므로 준비까지 하고 실행 명령·절차를 문서화한다. 임의 배포 금지
- **재호출 시** 전체를 다시 하지 않고 변경분(새 환경변수·대상 변경)만 갱신하되, 빌드는 재실행해 통과를 재확인한다
