# Website Studio Orchestrator

빌드 팀을 조율하여 **요구 분석 → 디자인 → API 계약 → 프론트·백엔드 병렬 구현(+점진 QA) → 통합 QA → 배포 준비**까지 한 번에 수행한다.

## 실행 모드: 에이전트 팀

전 Phase에서 에이전트 팀 모드를 사용한다. 팀원 간 직접 통신이 품질의 핵심 동력이기 때문이다 — **프론트엔드와 백엔드가 API 계약을 실시간으로 협상**해야 경계면 불일치가 처음부터 생기지 않고, QA가 각 모듈 완성 직후 양측에 즉시 수정을 요청해야 초기 버그가 후속 모듈로 전파되지 않는다. 이 교환을 리드가 일일이 중계하면 병목이 되고 계약 어긋남이 런타임까지 살아남는다.

## 왜 API 계약이 이 하네스의 심장인가

웹 앱 런타임 버그의 최대 원천은 "각각은 맞는데 연결부가 어긋남"이다. `{ projects: [...] }`를 반환하는 API와 배열을 기대하는 훅은 각자 정상이지만 함께 죽는다. TypeScript 제네릭·빌드 통과는 이 불일치를 못 잡는다. 그래서 이 하네스는 **구현 전에 API 계약(엔드포인트·응답 shape·필드 케이싱·상태코드·동기/비동기)을 확정하고 양측이 서명하게 한 뒤**, 프론트·백엔드가 그 계약만 바라보고 병렬로 짓게 한다. 계약이 유일한 진실이다.

## 경로 규약

이 하네스는 플러그인으로 배포된다. **모든 산출물 경로는 하네스를 실행 중인 프로젝트의 루트 기준 상대 경로**이며, 플러그인이 어디에 설치되었는지와 무관하다. 앱 코드 기본 루트는 `website/`(사용자가 기존 프로젝트에 지으라 하면 그 루트), 기획 산출물은 `website/_workspace/`다.

| 용도 | 경로 |
|------|------|
| 기획·검증 산출물 | `website/_workspace/` |
| 앱 코드 | `website/app/`, `website/components/`, `website/hooks/`, `website/lib/`, `website/app/api/` 등 |

에이전트 정의와 스킬은 플러그인이 제공하므로 **경로로 참조하지 않는다.** 에이전트는 `subagent_type`으로, 스킬은 Skill 툴의 스킬명으로 호출한다.

## 팀 구성

리더는 이 스킬을 실행하는 메인 세션이며, 빌드 리드 역할을 수행한다. 시작 시 `website-studio:build-lead` 정의를 리드 원칙으로 적용한다 — 메인 세션이 리더이므로 이 에이전트를 별도로 띄우지 않는다.

| 팀원 (`subagent_type`) | 사용 스킬 | 주 산출물 |
|------|----------|------|
| `website-studio:ux-designer` | `website-studio:ux-design` | `00_design_spec.md` |
| `website-studio:frontend-engineer` | `website-studio:frontend-build` | `website/app`, `components`, `hooks` + `02_frontend_log.md` |
| `website-studio:backend-engineer` | `website-studio:backend-build` | `website/app/api`, `lib` + `03_backend_log.md` |
| `website-studio:qa-inspector` | `website-studio:qa-inspection` | `04_qa_report.md` |
| `website-studio:deploy-engineer` | `website-studio:deploy-prep` | 배포 구성 + `05_deploy_checklist.md` |

**팀원 생성 방식:** 위 표의 `subagent_type`을 그대로 사용한다. 플러그인이 배포한 에이전트 정의가 자동 등록되므로, 정의 파일을 Read시키는 우회는 필요 없다 — 역할·원칙·통신 프로토콜이 시스템 프롬프트로 이미 주입된 상태로 기동한다. `model`은 전원 `opus`.

**프롬프트 필수 요소 (전 팀원 공통):** 에이전트 정의에는 역할만 있고 이번 실행의 경로·범위는 없다. 팀원은 프로젝트 루트에서 실행되므로 다음이 빠지면 파일을 엉뚱한 위치에 쓰거나 엉뚱한 것을 만든다.
1. **화면 목록(P번호)/담당 엔드포인트 등 이번 실행의 범위**
2. **입력 파일의 `website/_workspace/...` 전체 경로**
3. **앱 코드 루트와 출력 파일의 전체 경로**

## 워크플로우

### Phase 0: 컨텍스트 확인

`website/_workspace/` 존재 여부로 실행 모드를 정한다.

| 상태 | 모드 | 행동 |
|------|------|------|
| 미존재 | **초기 실행** | Phase 1로 진행 |
| 존재 + 사용자가 부분 수정 요청 | **부분 재실행** | Phase 1 건너뛰고 아래 "부분 재실행" 절차 |
| 존재 + 새 프로젝트/새 요구 | **새 실행** | `website/_workspace/`를 `website/_workspace_{YYYYMMDD_HHMMSS}/`로 이동 후 Phase 1 |

애매하면 사용자에게 묻는다. 기존 코드·계약을 덮어쓰는 것은 되돌리기 어렵기 때문이다.

**부분 재실행 절차:**
1. 대상을 특정한다 (예: "P3 대시보드 레이아웃만" → ux-designer / "프로젝트 목록 API에 페이지네이션" → backend + frontend + qa / "배포 준비만" → deploy-engineer)
2. **계약이 바뀌는가**를 먼저 판단한다. 응답 shape·필드·엔드포인트가 바뀌면 `01_api_contract.md`를 먼저 갱신하고 프론트·백엔드·QA를 함께 재소집한다. 계약이 그대로면 해당 팀원만 소집한다
3. 팀원 프롬프트에 **이전 산출물 경로 + 사용자 피드백 원문**을 그대로 포함한다. 요약하지 않는다 — 뉘앙스가 사라진다
4. 변경이 경계면에 닿으면 qa-inspector로 영향받는 경계면만 재검증한다
5. 코드가 바뀌었으면 Phase 5(배포 재확인)까지 진행

### Phase 1: 요구 분석 & 디자인 (리드 + ux-designer)

**실행 방식:** 리드(메인 세션)가 요구를 분해하고 사용자 확인 → ux-designer 소집.

1. 사용자 입력에서 다음을 파악한다. 없으면 묻는다:
   - **무엇을 만드는가** (필수 — 사이트 종류, 핵심 기능)
   - **기술 스택** (없으면 기본 제안: Next.js App Router + Route Handlers + 인메모리/파일 저장소 또는 사용자 지정 DB)
   - **디자인 톤 / 배포 대상** (없으면 조사 후 제안)
   - **범위/MVP 기대치** (없으면 표준: 핵심 화면 3~6개)
2. `website/_workspace/` 생성
3. 리드가 요구를 **화면 목록(P1~Pn) + 핵심 사용자 플로우**로 분해하고, **사용자에게 제시해 승인받는다.** 화면이 8개를 넘으면 MVP 우선순위를 물어 좁힌다
4. ux-designer 소집 → `00_design_spec.md` 작성 (화면 인벤토리·와이어프레임·디자인 토큰·컴포넌트 인벤토리·**화면별 데이터 요구**). 입력으로 화면 목록·플로우·톤, 출력 경로 전달

### Phase 2: API 계약 확정 (리드 + backend + frontend 서명)

**실행 방식:** 에이전트 팀 (frontend·backend 합류, 계약 협상)

이 Phase가 이 하네스의 핵심 게이트다. 구현 착수 전에 계약을 못박는다.

1. 리드가 `00_design_spec.md`의 화면별 데이터 요구에서 **데이터 모델 + 엔드포인트 목록**을 도출해 `01_api_contract.md` 초안을 쓴다. 각 엔드포인트에 다음을 명시:
   - 메서드 + 경로, 요청 shape, **응답 shape(정확한 필드명 + 케이싱)**, 상태코드, 동기/비동기 여부, 래핑 여부(`{ items: [...] }` vs 배열)
   - 데이터 모델: 각 엔티티의 필드명 + 타입 + DB↔API 케이싱 변환 규칙
2. frontend·backend 소집, 계약 초안 리뷰 요청:
   - frontend: "이 응답 shape으로 각 화면을 렌더할 수 있는가? 부족한 필드는?"
   - backend: "이 응답을 실제로 제공 가능한가? 불가능한 지점은?"
3. **통신 규칙:** 두 엔지니어가 SendMessage로 직접 협상해 계약을 수렴시킨다. 리드는 상충 시에만 판정한다
4. 양측 서명(합의) 후 리드가 `01_api_contract.md`를 확정한다. **이 계약이 이후 유일한 진실이다**

### Phase 3: 병렬 구현 + 점진 QA

**실행 방식:** 에이전트 팀 (frontend ∥ backend 동시 구현, qa-inspector 점진 검증)

1. TaskCreate: frontend에 "P번호별 화면·훅 구현", backend에 "엔드포인트별 구현" 작업 등록. 계약을 기준으로 독립 병렬 진행
2. **통신 규칙 — 이 Phase의 핵심 (리드를 경유하지 않는다):**
   - 구현 중 계약을 바꿔야 하면(예: 백엔드가 특정 필드 제공 불가), 임시방편으로 때우지 않고 상대·리드에게 알려 **계약을 먼저 갱신**한 뒤 재개한다
   - 프론트·백엔드는 **같은 계약의 엔드포인트로 작업을 태깅**한다. 이것이 QA 교차 비교의 정렬 축이다
3. **점진 QA:** 각 엔드포인트/화면 모듈이 완성되면 담당 엔지니어가 qa-inspector에 통지 → qa-inspector가 즉시 그 경계면(API 응답↔대응 훅)을 교차 검증하고, 불일치를 **양측 모두에게** 파일:라인 + 수정 방향으로 SendMessage. 전체 완성까지 미루지 않는다
4. 리드는 병렬성을 죽이지 않도록 개입을 최소화하되, 계약 재협상이 보고되면 즉시 중재한다

### Phase 4: 통합 QA (전면 경계면 교차 검증)

**실행 방식:** 에이전트 팀 (qa-inspector 주도, 엔지니어 대기)

1. qa-inspector 소집, 입력으로 `01_api_contract.md` + `02/03_log.md` + 앱 코드 전체 지정
2. TaskCreate: "통합 정합성 전면 검증 → `04_qa_report.md`" — API↔훅 shape, 응답 래핑, 케이싱, 라우팅(파일경로↔href), 상태 전이(맵↔코드), 엔드포인트 1:1 매핑, 동기/비동기. 가능하면 `npm run build`·타입체크 실행
3. 검증 완료 → `04_qa_report.md`의 **실패 항목** 확인
4. **실패 없음 / 경미** → Phase 5
5. **경계면 실패 있음** → 수정 루프:
   - qa-inspector가 각 실패를 생산자/소비자로 분류해 담당 엔지니어에게 파일:라인 + 수정 방향 전달 (경계면은 양측 모두)
   - 담당 엔지니어가 해당 부분만 수정 (계약이 옳으면 구현을 계약에 맞추고, 계약이 틀렸으면 리드가 계약을 갱신 후 양측 수정)
   - qa-inspector가 **수정된 경계면만** 재검증
   - **최대 2회.** 3회차 진입 시 남은 이슈를 `04_qa_report.md`에 "미해결"로 확정하고 사용자 보고에 명시한 뒤 Phase 5로 넘어간다

### Phase 5: 배포 준비

**실행 방식:** 에이전트 팀 (deploy-engineer 합류)

1. deploy-engineer 소집, 입력으로 앱 코드 전체 + `04_qa_report.md`(미해결 이슈) + 배포 대상 지정
2. TaskCreate: "빌드 구성·환경변수 점검, **프로덕션 빌드 실행**, 배포 대상 구성, 리스크 플래그 → `05_deploy_checklist.md`"
3. **통신 규칙:** 프로덕션 빌드가 코드 결함으로 실패하면 deploy-engineer가 담당 엔지니어에게 수정 요청(빌드를 억지로 통과시키는 우회 금지). 임시 저장소·목 데이터를 backend에 확인해 배포 리스크로 승격
4. 완료 조건: 프로덕션 빌드 통과가 증거(빌드 로그)와 함께 기록되고, 환경변수 목록·배포 절차·배포 전 리스크가 체크리스트에 채워질 것

### Phase 6: 통합 및 정리

1. 리드가 최종 결과를 직접 확인한다:
   - 구현된 화면이 디자인 스펙의 P번호를 모두 커버하는가 (미구현은 명시됐는가)
   - QA 리포트의 경계면 실패가 해소됐거나 "미해결"로 명시됐는가
   - 프로덕션 빌드가 실제로 통과했는가 (증거 있는가)
   - 임시 저장소·목 데이터 등 배포 리스크가 숨겨지지 않고 체크리스트에 살아 있는가
2. 팀원에게 종료 알림 → `TeamDelete`
3. `website/_workspace/`는 **삭제하지 않는다** (사후 검증·부분 재실행의 입력)
4. 사용자에게 요약 보고: 구현된 화면·API, QA 통과/미해결, 빌드 상태, 배포 절차, 앱 실행 방법
5. 피드백 요청: "결과에서 개선할 부분이나 팀 구성에서 바꾸고 싶은 점이 있나요?"

```

    ↓
[리드] 화면 분해(P번호) → 사용자 승인
    ↓
ux-designer → 00_design_spec.md (화면·토큰·데이터 요구)
    ↓
[리드] 계약 초안 → 01_api_contract.md
    ↓ frontend ⇄ backend 협상·서명
01_api_contract.md (확정 — 유일한 진실)
    ↓ 병렬 구현 (계약만 바라봄)
 ┌────────────────────┬────────────────────┐
 ↓                    ↓            (SendMessage로 계약 변경 협상)
frontend-engineer     backend-engineer
website/app,hooks     website/app/api,lib
02_frontend_log.md    03_backend_log.md
 └─────────┬──────────┴────────────────────┘
   각 모듈 완성 즉시 ↓ 점진 QA (양측 통지)
qa-inspector → 경계면 교차 비교(API 응답↔훅, 라우팅, 상태전이)
```

## 에러 핸들링

| 상황 | 전략 |
|------|------|
| 계약 상충 (프론트 요구 ≠ 백엔드 가능) | 삭제하지 않고 양측 재협상, 결정 근거를 계약서에 기록. 리드가 판정 |
| 엔지니어가 계약 우회(임시 shape) | 반려. 계약을 먼저 갱신하고 양측 전파 후 구현 — 우회는 다음 경계면 버그의 씨앗 |
| 점진 QA에서 경계면 불일치 | 양측 모두에게 파일:라인 + 수정 방향 통지. 어느 쪽이 계약을 어겼는지 판정 후 수정 |
| 빌드 통과했으나 런타임 shape 불일치 의심 | qa-inspector가 계약서와 실제 응답을 직접 대조 (제네릭 캐스팅은 컴파일 통과함) |
| 팀원 1명 실패 | SendMessage로 상태 확인 → 1회 재시작 → 재실패 시 해당 범위를 "미구현"으로 명시하고 진행 |
| 프로덕션 빌드 실패 | deploy가 원인 특정 → 담당 엔지니어 수정 요청. 타입체크/린트 무시로 우회 금지 |
| QA 수정 루프 3회차 | 루프 종료. 남은 경계면 이슈를 "미해결"로 확정, 사용자 보고에 명시 |
| 임시 저장소/목 데이터 | 삭제하지 않고 배포 체크리스트에 "배포 전 교체 필요"로 승격 |
| 요구가 너무 큼 | 리드가 MVP 우선순위를 물어 1차 범위를 좁힘. 억지로 다 지으면 모든 화면이 얕고 QA가 못 따라감 |
| 팀원 과반 실패 | 사용자에게 알리고 진행 여부 확인 |

## 테스트 시나리오

### 정상 흐름
1. 사용자: "프로젝트를 카드로 보여주는 대시보드가 있는 할 일 관리 웹앱 만들어줘. Next.js로."
2. Phase 1 — 리드가 화면 4개 분해(P1 랜딩, P2 로그인, P3 대시보드, P4 프로젝트 상세), 사용자 승인 → ux-designer가 디자인 스펙 작성(P3 카드: 제목·상태 배지·수정일)
3. Phase 2 — 리드가 계약 초안(`GET /api/projects` → `{ projects: Project[] }`, `Project`={ id, title, status, updatedAt }), frontend·backend가 협상·서명
4. Phase 3 — frontend는 `useProjects` 훅이 `.projects`를 unwrap하도록, backend는 정확히 `{ projects: [...] }`를 camelCase로 반환하도록 병렬 구현. `GET /api/projects` 완성 즉시 QA가 훅↔응답 교차 검증 → 통과
5. Phase 4 — 통합 QA: 라우팅(`/dashboard/projects/[id]` href 매칭), 상태 전이(todo→doing→done 코드 존재), 빌드 실행 → 통과
6. Phase 5 — deploy가 `next build` 통과 확인, `.env.example` 생성, 인메모리 저장소를 "배포 전 DB 교체 필요"로 플래그
7. Phase 6 — 리드가 4개 화면·API 매핑·빌드 통과 확인, 사용자에게 실행법(`npm run dev`)·배포 절차 보고

### 에러 흐름 A — 경계면 불일치 발견
1. Phase 3에서 backend가 `GET /api/projects`를 배열 `[...]`로 반환, frontend 훅은 계약대로 `{ projects: [...] }`의 `.projects`를 기대
2. 해당 API 완성 통지 → 점진 QA가 계약서와 실제 응답을 대조, backend가 계약(`{ projects }` 래핑)을 어긴 것으로 판정
3. qa-inspector가 backend에 "route.ts:12 — 계약은 `{ projects: [...] }` 래핑, 현재 배열 반환. 래핑 추가" 수정 요청, frontend에도 경계면 이슈로 통지
4. backend 수정 → QA 재검증 통과. 런타임 `x.filter is not a function` 크래시를 구현 단계에서 차단

### 에러 흐름 B — 프로덕션 빌드 실패
1. Phase 5에서 `next build`가 타입 에러로 실패 (프론트가 계약에 없는 필드 접근)
2. deploy가 빌드 로그에서 원인 특정, frontend에 수정 요청 (타입체크 무시 우회 금지)
3. frontend가 계약에 맞춰 수정 → deploy가 빌드 재실행 → 통과
4. 빌드 통과를 증거와 함께 `05_deploy_checklist.md`에 기록, "빌드 통과 없이 배포 준비 완료로 보고하지 않음" 원칙 유지
