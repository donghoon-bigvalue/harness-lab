# Report Integration — 리뷰 리포트 통합

검증이 끝난 발견을, **심각도로 우선순위가 매겨진 하나의 리뷰 리포트**로 엮는다. 새 발견을 만들지 않고 검증된 것을 정직하게 배열해, 리뷰를 받는 사람이 무엇부터 고칠지 바로 알게 한다.

## 작성 절차

### 1. 입력 구조 파악
`05_verification.md`(주 입력)의 확인/오탐/교차/미결을 읽고, `00_scope.md`의 대상·심각도 기준과 리드의 통합 방향(`06_integration_brief.md`, 있으면)을 맞춘다. 근거 인용이 필요하면 원 감사 파일(01~04)의 레코드를 추적한다. **'확인'으로 분류된 것만 본문에 싣는다.**

### 2. 심각도 순으로 배열
확인된 발견을 정규화 심각도 순으로 정렬한다. Critical이 스크롤 위쪽에. 실행 요약만 읽어도 무엇부터 볼지 알 수 있어야 한다. 검증 상태를 어조에 반영한다:

| 검증 상태 | 서술 어조 |
|----------|----------|
| 확인 | 단정 — "X이다" |
| 미결 | 유보 — "판정 보류: 완화 확인 필요" |
| 교차 | 양축 병기 — "성능 병목이자 DoS 벡터" |

### 3. 교차 발견을 부각한다
성능이자 보안인 발견을 단일 축 섹션에 묻지 않는다. 별도 소절로 드러낸다 — 네 축을 하나로 리뷰한 통합의 핵심 가치다.

### 4. 권장 수정 순서를 제시한다
심각도 × 수정 비용·의존을 고려한 실행 순서를 제안한다. "무엇부터, 왜"가 리뷰 대상자에게 가장 실용적이다.

### 5. 정직하게 한계를 적는다
미감사 축, 실측 못 한 성능 추정, 완화 미확인 보안 발견, 좁힌 범위를 "한계"에 명시한다. 오탐은 부록에 남긴다(본문 제외). `05_verification.md`에 없는 발견을 채워 넣지 않는다.

## 리포트 구조

최종 경로(기본 `code-review/outputs/{YYYYMMDD}-{slug}/code-review-report.md`, 감독자가 지정):

```markdown
# {리뷰 대상} — 코드 리뷰 리포트
> 리뷰일: {YYYY-MM-DD} | 감사 축: 아키텍처·보안·성능·스타일 | 검증: 트리아지·심각도 정규화

## 실행 요약
- 리뷰 대상: {파일/diff 범위}
- 발견 총계: Critical {n} · High {n} · Medium {n} · Low {n} · Info {n}
- 가장 시급한 3~5건: {ID + 한 줄}
- 전반 평가: {한 문단}

## 1. Critical / High 발견
{ID·위치·심각도·근거·영향·권고. 단정적 어조}

## 2. Medium / Low / Info 발견
{축별 또는 심각도별 정리}

## 3. 교차 발견 (축을 넘나드는 결함)
{묶인 발견 + 양축 관점 + 통합 심각도}

## 4. 권장 수정 순서
{심각도 × 비용·의존 기준의 실행 순서}

## 5. 리뷰의 한계
- 미감사 축: {}
- 실측 못 한 성능 추정: {}
- 완화 미확인 보안 발견(미결): {}
- 범위 축소·표본 한계: {}

## 부록 A. 오탐으로 걸러진 발견
{제거된 발견 + 왜 오탐인가 — 재검토 가능하게}
```

## 핵심 원칙

- **심각도가 곧 순서다.** Critical부터, 실행 요약이 우선순위를 드러낸다.
- **새 발견을 만들지 않는다.** '확인'된 것만 본문에. 오탐은 부록.
- **검증 상태를 어조에 반영한다.** 확인은 단정, 미결은 유보.
- **교차 발견을 부각한다.** 통합의 핵심 가치를 묻지 않는다.
- **정직하게 한계를 적는다.** "안 나옴"과 "안 봄"을 구분한다. 확인 0건이면 그것이 정직한 결론이다 — 억지 항목 금지.
- **코드를 고치지 않는다.** 산출물은 리포트다. 권고는 방향 제시까지.
