# Style Audit — 코드 스타일·가독성 감사

코드가 "읽고 유지보수하기 좋은가, 주변 코드와 일관되는가"를 감사한다. 목표는 개인 선호 강요가 아니라, **코드베이스의 기존 관례를 기준으로 가독성·일관성 마찰**을 지목하는 것이다. 모듈 경계·결합은 아키텍처 축이고, 이름·포맷·중복·주석·국소 가독성이 이 축이다.

## 감사 절차

### 1. 기존 관례를 먼저 파악한다
감사 전에 대상 주변 코드를 읽어 우세한 패턴(네이밍·포맷·에러 처리 방식)을 파악한다. 프로젝트에 린터·포매터 설정·컨벤션 문서가 있으면 **그것이 기준**이다. 없으면 코드베이스 우세 패턴이 기준. 당신의 개인 선호는 기준이 아니다.

### 2. 점검 축
| 축 | 무엇을 보는가 |
|----|--------------|
| **일관성** | 주변 관례와 어긋나는 네이밍·포맷·패턴. 새 코드가 기존 컨벤션을 따르는가 |
| **가독성** | 모호한 이름, 과도한 중첩, 마법 숫자, 지나치게 긴 함수, 이해를 막는 표현 |
| **중복·데드** | 복붙 로직, 도달 불가 코드, 미사용 심볼 |
| **주석·에러 처리** | 오해/낡은 주석, 삼켜진 예외, 일관되지 않은 에러 처리 |

### 3. 취향과 결함을 구분한다
"탭 대 스페이스" 같은 순수 선호는 소음이다. "이 파일은 스페이스인데 이 함수만 탭이라 일관성이 깨진다"가 발견이다. 자동 포매터가 잡는 것(들여쓰기·세미콜론)은 대개 Low/Info. 도구가 못 잡는 것(오해 부르는 이름, 삼켜진 에러)이 더 가치 있다.

### 4. 심각도·확신도 태깅
스타일은 대개 Low/Info. 단, **삼켜진 예외처럼 버그를 숨기는 스타일은 심각도를 올리고** 정확성 함의를 근거에 적어 해당 축 감사원에게 넘긴다. 관례 확인 후 판단은 '확실', 관례 불명 추정은 '추정'.

## 출력 형식

`code-review/_workspace/04_style_findings.md` (감독자가 전달한 정확한 경로 사용):

```markdown
# 스타일 감사 결과
> 감사 대상: {파일 목록/diff} | 참조 관례: {린터 설정/컨벤션 문서/코드베이스 우세 패턴}

## 발견

### STYLE-1. {한 줄 요약} [style]
- 위치: {파일:줄}
- 심각도: Critical|High|Medium|Low|Info — {대개 Low/Info, 버그 은폐 시 상향}
- 확신도: 확실|추정|의심 — {관례 확인 여부}
- 근거: {어긋난 관례/가독성 원칙 + 코드 인용 + 기존 관례와의 대비}
- 영향: {유지보수·이해 마찰, 버그 은폐 가능성}
- 권고: {코드베이스 우세 패턴에 맞춘 개선}

### STYLE-2. ...

## 감사 커버리지
- 참조한 관례 근거: {무엇을 기준 삼았는가}
- 관례 불명으로 추정에 그친 부분: {}
- 다른 축에 넘긴 지점: {삼켜진 예외 등을 보안/성능에 공유}
```

## 핵심 원칙

- **취향이 아니라 코드베이스 관례가 기준이다.** 감사 전 주변 코드를 읽는다.
- **설정된 관례를 우선한다.** 린터/포매터/컨벤션 문서 > 우세 패턴 > 개인 선호.
- **도구가 못 잡는 것에 집중한다.** 오해 부르는 이름·삼켜진 에러가 순수 포맷보다 가치 있다.
- **취향과 결함이 안 갈리면 올리지 않는다.** 소음이 리포트의 신호 대 잡음비를 떨어뜨린다.
