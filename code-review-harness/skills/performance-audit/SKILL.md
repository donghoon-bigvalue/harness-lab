# Performance Audit — 성능 병목 감사

코드가 "규모·부하가 커질 때 어디서 무너지는가"를 감사한다. 목표는 미세 최적화 지적이 아니라, **문제가 드러나는 조건(입력 규모·실행 빈도)과 함께 실제 병목**을 지목하는 것이다.

## 감사 절차

### 1. 핫패스를 먼저 식별한다
요청마다·루프마다 도는 경로를 찾는다. 초기화 1회 코드의 미세 비효율은 Low 이하다. 실행 빈도가 심각도의 절반을 결정한다.

### 2. 병목 카테고리 점검
| 카테고리 | 무엇을 보는가 |
|----------|--------------|
| **복잡도·자료구조** | 불필요한 O(n²), 반복 내 선형 탐색, 잘못된 자료구조, 중첩 루프 |
| **I/O·쿼리** | N+1 쿼리, 루프 내 원격 호출, 배치 가능한 개별 처리, 인덱스 미사용, 블로킹 I/O |
| **메모리·할당** | 핫패스 불필요 할당·복사, 누수, 무제한 버퍼링·캐시 |
| **동시성·확장성** | 락 경합, 직렬화 병목, 캐싱 기회, 부하 증가 시 선형 이상 악화 |

### 3. 조건과 규모를 명시한다
각 발견에 "어떤 입력 규모·부하에서 얼마나 악화되는가"를 적는다. "느리다"는 발견이 아니다. "N명당 N쿼리 → N=1000이면 요청당 1000쿼리"가 발견이다.

### 4. 측정과 추정을 구분한다
복잡도·쿼리 패턴처럼 코드만으로 확정되는 것은 '확실'. 실측 없이 "느릴 듯"은 '추정'/'의심'. 확신도를 부풀리지 않고, 조기 최적화(병목 근거 없는 개선)는 올리지 않는다.

## 출력 형식

`code-review/_workspace/03_performance_findings.md` (감독자가 전달한 정확한 경로 사용):

```markdown
# 성능 감사 결과
> 감사 대상: {파일 목록/diff} | 감사 모드: {정상 | 제한적}

## 발견

### PERF-1. {한 줄 요약} [perf]
- 위치: {파일:줄 또는 함수/쿼리}
- 심각도: Critical|High|Medium|Low|Info
- 확신도: 확실|추정|의심 — {정적 확정 / 실측 없는 추정}
- 근거: {병목 유형 + 복잡도/실행 빈도 + 코드 인용}
- 영향: {어떤 규모·부하에서 얼마나 악화, 사용자 체감/자원 한계}
- 권고: {배치·인덱스·캐시·자료구조 교체 등 + 트레이드오프}

### PERF-2. ...

## 감사 커버리지
- 확정한 병목: {}
- 실측 불가로 추정에 그친 부분: {}
- 다른 축에 넘긴 지점: {DoS로 보안에, 구조적 근원으로 아키텍처에 공유한 발견}
```

## 핵심 원칙

- **조건과 규모 없는 발견은 올리지 않는다.** 문제가 드러나는 입력을 적는다.
- **핫패스인지 확인한다.** 실행 빈도가 심각도를 좌우한다.
- **측정과 추정을 구분한다.** 실측 없는 것은 '추정' 이하 + "실측 필요".
- **조기 최적화를 권하지 않는다.** 병목 근거가 있을 때만 발견이다.
