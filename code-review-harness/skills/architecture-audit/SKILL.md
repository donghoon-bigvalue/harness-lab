# Architecture Audit — 아키텍처·구조 감사

코드의 "어떻게 조직되어 있는가"를 감사한다. 목표는 우아함 평가가 아니라, **변경·확장·이해·테스트를 막거나 비싸게 만드는 구조 결함을 구체적 비용과 함께 지목**하는 것이다.

## 감사 절차

### 1. 대상 정렬
리드가 준 대상 파일 목록과 심각도 기준을 먼저 읽는다. 대상이 여러 파일이면 **파일·모듈 간 의존 그래프를 먼저 그린다** — 누가 누구를 import/호출하는가. 국소 함수만 봐서는 구조 결함이 안 보인다.

### 2. 점검 축
| 축 | 무엇을 보는가 |
|----|--------------|
| **책임 분리** | god object/함수, 뒤섞인 관심사, 단일 책임 위반, 비대한 인터페이스 |
| **결합·의존 방향** | 순환 의존, 잘못된 계층 의존(상위↔하위 역전), 구현 세부 결합, 전역 상태 공유 |
| **추상화 품질** | 누수 추상화, 잘못된 경계, 조기/과잉 추상화, 중복 개념, 새는 캡슐화 |
| **확장·변경·테스트** | 새 요구 시 뜯을 범위, 하드코딩된 결합으로 목킹/테스트 불가, 변경의 파급 |

### 3. 구체적 비용으로 판정
각 발견에 "이 구조 때문에 무엇을 하려 할 때 무엇이 얼마나 드는가"를 적는다. "결합도 높음" 같은 라벨은 발견이 아니다. 구체적 변경 시나리오(예: "DB 교체 시 3개 서비스를 함께 수정해야 함")가 근거다.

### 4. 심각도·확신도 태깅
리드의 공통 기준으로 심각도를, 맥락 확보 정도로 확신도를 매긴다. 전체 그래프를 못 본 추정은 '추정' 이하.

## 출력 형식

`code-review/_workspace/01_architecture_findings.md` (감독자가 전달한 정확한 경로 사용):

```markdown
# 아키텍처 감사 결과
> 감사 대상: {파일 목록/diff} | 감사 모드: {정상 | 제한적}

## 발견

### ARCH-1. {한 줄 요약} [arch]
- 위치: {파일:줄 또는 모듈/클래스}
- 심각도: Critical|High|Medium|Low|Info
- 확신도: 확실|추정|의심 — {근거}
- 근거: {구조 결함 유형 + 구체적 변경/이해 비용 + 코드 인용}
- 영향: {향후 어떤 변경·확장·테스트를 막거나 비싸게 하는가}
- 권고: {개선 방향 + 트레이드오프}

### ARCH-2. ...

## 감사 커버리지
- 충분히 감사한 영역: {}
- 맥락 부족으로 추정에 그친 영역: {무엇을 못 봤는지}
- 다른 축에 넘긴 지점: {성능/보안 근본원인으로 공유한 발견}
```

## 핵심 원칙

- **취향이 아니라 변경 비용으로 말한다.** 근거 없는 구조 선호는 소음이다.
- **큰 그림을 먼저 본다.** 의존 그래프 없이 국소만 보면 순환·역전을 놓친다.
- **추정을 확정으로 올리지 않는다.** 못 본 맥락은 커버리지에 남긴다.
- **못 본 것을 기록하는 것도 결과다.** 검증관이 신뢰도를 조정하는 근거가 된다.
